# Courier Ledger — Product Requirements Document v0.3

**Дата:** 2026-11-05  
**Статус:** концепция / согласованные решения и открытые вопросы  
**Цель:** сервис для личного и совместного учета выручки, прибыли, расходов и взаиморасчетов курьеров.  
**Языки MVP:** ru, cs, en. **Валюты MVP:** CZK, EUR, USD, UAH (ISO 4217; отдельные учётные валюты без автоматического FX на первом этапе).

## 1. Проблема и ценность

Курьеры получают выручку от разных сервисов, платят комиссии флотам, тратятся на топливо, аренду автомобилей, работают в одиночку или вместе с напарниками. Простые таблицы плохо отделяют *заработанную прибыль* от *фактического движения денег* и не позволяют безопасно вести совместный учет при сохранении приватности личных смен.

**Ценность:** после каждой смены быстро зафиксировать данные и увидеть реальную операционную прибыль каждого человека, команды, эффективность платформ и задолженность между участниками.

## 2. Согласованные решения

1. Пользователи регистрируются и входят по email/паролю и Google; Facebook/X — позднее.
2. Совместный учет через рабочие пространства (`workspace`) и приглашения.
3. Командный результат включает **только совместные смены и явно общие расходы**. Личные смены, личный доход и персональные отчеты не входят в командные агрегаты и недоступны другим участникам.
4. Общая смена: равные доли по умолчанию; пользователь может изменить доли, сумма долей = 100%.
5. Расход фиксирует, кто оплатил и на кого он распределен; долговые остатки отдельно от прибыли.
6. Различающиеся составы участников в течение дня — отдельные смены на MVP.
7. Mobile-first с полноценным desktop UX.
8. Интерфейс переводится на русский, чешский, английский с MVP.
9. Изменения совместной смены применяются после подтверждения обоих участников; оригинал доступен до утверждения.
10. Для каждой общей смены выбирается один **фактический получатель выплаты**. Это влияет на долг между участниками, но не на размер их прибыли.
11. Аренда хранит фактические даты начала и окончания; отчеты относят стоимость к периоду по пересечению дат и принятой политике распределения по дням.
12. В настройках пользователь выбирает CZK/EUR/USD/UAH; для общих пространств валюта учёта задается отдельно и едина для всех совместных операций. Никакого простого изменения символа валюты без пересчёта суммы.

## 3. Пользовательские сценарии

- **Solo:** курьер заносит единоличную смену, видит личный доход и расходы.
- **Duo:** участник добавляет общую смену, приглашенный напарник подтверждает данные и доли; оба видят результат.
- **Гибрид:** в один день пользователь отдельно заносит совместную и личную смены.
- **Аренда:** участник оплачивает автомобиль за фактический период (например, 09–15 ноября); расход распределяется по долям, долг возникает перед плательщиком, а отчеты учитывают пересечение периода аренды с периодом отчета.
- **Команда:** общий отчет строится **только по совместным сменам и общим расходам**; чужие личные смены (включая агрегаты) недоступны.
- **Изменения:** инициатор предлагает исправление совместной смены; другой участник видит diff и подтверждает/отклоняет.

## 4. MVP-функциональные требования

### 4.1 Аккаунт и участники
- Email/пароль, восстановление пароля, Google OAuth; изменение профиля (ник, язык, предпочитаемая валюта учёта); изменение email/пароля в безопасном auth-flow.
- Личный кабинет создается для каждого нового аккаунта.
- Создание workspace с фиксированной учётной валютой из CZK/EUR/USD/UAH, инвайт по ссылке/коду с ограничением по времени; роли `owner/member`. Изменение валюты workspace с имеющимися финансовыми записями запрещено до появления отдельной процедуры конвертации.
- Участники могут иметь личные смены и общие смены. Удаление участника не должно автоматически удалять бухгалтерскую историю.

### 4.2 Автомобили и платформы
- Список автомобилей, название, тип `owned/rented`, расход топлива по умолчанию, архивирование.
- Аренда: реальный период `starts_at/ends_at`, цена и валюта, плательщик, доли распределения между участниками. В MVP — явные договорные периоды; шаблон повтора на неделю/месяц может создавать последующие уникальные периоды. За период не должно возникать дублирующихся начислений.
- Пользовательские ставки комиссии для Bolt Food, Foodora, Wolt, других платформ (расширяемый список).
- В каждой смене фиксировать **снимок комиссии**, расхода, цены топлива и валюту; изменение настроек не пересчитывает прошлые смены автоматически.

### 4.3 Смена
Обязательные данные: дата, начало, окончание, платформа, автомобиль/иной тип транспорта, километры, расход л/100 км, цена топлива, количество заказов, общая выручка и её валюту, участники и их доли; для совместной смены — фактический получатель выплаты. Необязательные: примечания, реальный объем топлива, прочие затраты.

- Валидация: неотрицательные деньги/км/заказы, время окончания > начала (включая переход через полночь), доли в сумме = 100%.
- Время и дата хранятся как timestamp с часовым поясом; при отображении учитывается часовой пояс пользователя.
- Повторяющиеся шаблоны заполняют форму, но пользователь подтверждает фактические значения.
- Изменение соло-смены немедленное; изменение общей смены — версия `pending` с подтверждением второго участника.
- На MVP общая смена допускает ровно двух участников; модель БД остается расширяемой на N участников.

### 4.4 Расходы и взаиморасчеты
- Расходы: `fuel`, `rental`, `maintenance`, `other` с суммой, валютой, датой/периодом, плательщиком и распределением обязанностей по участникам.
- Топливо смены рассчитывается `km * l_per_100km / 100 * fuel_price`; можно ввести фактически потраченные литры, если известны.
- Общие расходы распределяются по согласованным долям, независимо от того, кто их оплатил.
- Доход участника и его доля затрат входят в операционную прибыль; платеж одного участника за другого формирует задолженность.
- Фактический расчет по задолженности (`settlement transfer`) закрывает долг, **не изменяя прибыль**.
- Для общей смены **обязательно** фиксировать одного фактического получателя всей выплаты (для корректного расчёта долга). В следующих версиях можно поддержать несколько частичных получателей.

### 4.5 Отчеты
- Периоды: день / неделя / месяц / пользовательский диапазон.
- Персонально: все свои смены и назначенные затраты; по workspace: **только совместные смены и общие расходы**. Показатели: выручка, комиссия, топливо в литрах и выбранной валюте, аренда, прочие расходы, операционная прибыль, часы, км, заказы, прибыль/час, выручка/час, прибыль/заказ. Никогда не суммировать разные валюты без явной конвертации.
- Отдельная карточка «взаиморасчеты / кто кому должен» в учётной валюте workspace.
- Для аренды отчет признаёт только часть стоимости, пересекающую выбранный период (по календарным дням в часовом поясе workspace); экран текущих обязательств отдельно показывает полную согласованную стоимость аренды, оплаченной вперед.
- Экспорт CSV и JSON для собственных доступных данных; в командных отчетах чужие приватные исходные записи не экспортируются.

### 4.6 Приватность, безопасность, целостность
- Строковая авторизация RLS, не только фильтры UI. `private` смены доступны только владельцу; `shared` смены доступны ее участникам.
- Командные итоги **не включают приватные смены**; API/RLS не выдают ни их исходные записи, ни агрегированные данные.
- Сводные командные показатели включают только публичные для участников совместные операции; таким образом личные смены не выдаются через разность общего и собственного результата.
- Изменения совместных смен/расходов сохраняют журнал ревизий и состояния согласования.
- Денежные значения — целые минимальные единицы соответствующей валюты (`minor units`, все четыре выбранные валюты сейчас используют 2 десятичных знака) или точные decimal на сервере, без float для финансовых итогов; обязательное поле `currency_code`.
- Запрет на массовую подмену `workspace_id`, `owner_user_id` и долей через клиентский API. Перерасчет и подтверждение — атомарные транзакции.
- Отдельно тестируем изоляцию разных workspaces и сценарии удаления/выхода участника.

## 5. Финансовые показатели и формулы

**Смена**
- `fuel_liters = distance_km × consumption_l_per_100km / 100`, если не задано фактическое значение.
- `fuel_cost = fuel_liters × price_per_liter`.
- `commission = gross_revenue × commission_rate`.
- `shift_operating_profit = gross_revenue − commission − fuel_cost − other_shift_expenses`.
- `personal_shift_profit = share(gross_revenue) − share(commission) − allocated_fuel − allocated_other_expenses`.

**За период**
- Аренда распределяется по пересечению **реального периода аренды** с выбранным отчётным интервалом, пропорционально календарным дням в часовом поясе workspace (итог разнесённых частей точно равен полной стоимости).
- `operating_profit = Σ personal_shift_profit − Σ allocated_rental_and_recurring_expenses`.
- `profit_per_hour = operating_profit / worked_hours` (если hours > 0; при нуле выводить «—»).
- `net_balance_between_members` вычисляется из *фактических получателей выручки*, *фактических плательщиков расходов*, *назначенных долей* и *закрывающих платежей*.

**Пример аренды:** 1 500 Kč/неделя, плательщик A, 50/50. У A и B расход по 750 Kč. B должен A 750 Kč. При переводе B→A 750 Kč задолженность закрывается, но прибыль A/B не меняется.

## 6. Критерии приемки MVP

1. Пользователь A не может получить через API личную смену пользователя B по чужому ID.
2. Изменение комиссии в настройках не меняет историческую прибыль.
3. Две разные смены одного дня (duo + solo) отражаются в личном результате точно по долям.
4. При аренде 1 500 Kč/неделю, разделенной пополам, у каждого появляется −750 Kč, а не −1 500 Kč и не повторные списания при обновлении страницы.
5. Если A оплатил аренду, задолженность B→A = 750 Kč; ее погашение не увеличивает прибыль.
6. Неподтвержденная правка общей смены не меняет опубликованные показатели обоих пользователей.
7. Dashboard одинаково правильно считает после повторного входа с другого устройства.
8. Общий Dashboard не содержит ни суммы, ни списка чужих личных смен; личные отчеты изолированы.
9. Смена на 2 000 Kč с получателем A и долями 50/50 создаёт обязательство A→B на 1 000 Kč до расходов; запись погашения долга не увеличивает прибыль.
10. Аренда Wed–Tue (7 суток) на 1 500 Kč в недельном отчете Mon–Sun распределяется по пересечению 5/7, в следующем — 2/7; сумма двух отчётов точно 1 500 Kč.
11. Для CZK/EUR/USD/UAH создаются самостоятельные пространства, сохраняются валюты записей и корректно форматируются суммы; переключение языка не меняет валюту и не конвертирует числа.
12. Полный сценарий регистрации, добавления автомобиля и платформы, инвайта, общей смены, согласования, анализа и экспорта работает на телефоне и desktop.
13. Интерфейс имеет переводы ru/cs/en, без непереведенных критичных экранов.

## 7. Что не входит в MVP

- Финансовые рекомендации и автоматический расчет налогов/страховых взносов.
- Банковские интеграции и прямые интеграции с аккаунтами Bolt/Foodora/Wolt.
- Платежи между пользователями внутри приложения.
- Трекер GPS, маршрутная оптимизация, фоновое определение пробега.
- Несколько смен-сегментов в одной записи.
- Facebook/X вход, платные тарифы, офлайн-синхронизация, push-уведомления, импорт с дедупликацией.

## 8. Уточнения перед окончательной SQL-схемой

- **Валюта:** РЕШЕНО в v0.4 — только базовая валюта учёта для новых workspaces; никаких автоматических пересчетов истории.
- **Выплаты:** различать начисленные платформой средства и реально полученную выплату; рекомендуем хранить дату и статус получения.
- **Аренда:** при досрочном прекращении периода/изменении долей создавать аудируемую корректировку с согласованием.
- **Редактирование:** кто может отменить неподтвержденный запрос изменения и через какой срок он истекает.
- **Рабочие часы:** общая смена засчитывается обоим участникам в полном объёме, при этом часы работы команды как временные интервалы не суммируются дважды.
- **Автомобили:** в MVP машина принадлежит одному пользователю и может быть доступна для выбора остальным в workspace с разрешения владельца.

## 9. Предварительный стек (не заморожен)

React + TypeScript + Vite; Tailwind CSS + компонентная библиотека; Supabase Auth + PostgreSQL + RLS и серверные SQL-функции/Edge Functions для транзакционных операций; Cloudflare Pages для фронтенда; Vitest и Playwright. Решение о деплое и смете фиксируется отдельно перед началом кодинга.

## 10. Мультивалютность (решение для MVP)

- Поддерживаем ISO 4217: `CZK`, `EUR`, `USD`, `UAH`. Это **валюты учёта**, не язык интерфейса. `ru/cs/en` — отдельная настройка.
- Пользователь выбирает предпочитаемую валюту при регистрации и может менять её для **новых рабочих пространств**. Совместное пространство получает собственную валюту при создании; участники видят общие записи в ней, независимо от личных предпочтений.
- Каждая денежная запись содержит свой `currency_code` и сумму в minor units. Все доходы и расходы в одном пространстве MVP должны быть в его учётной валюте. Это даёт корректные балансы без внешнего FX API.
- Изменение выбора на EUR **не превращает** старые 1 000 CZK в 1 000 EUR. Для существующего непустого пространства требуется отдельный конверсионный workflow (после MVP) либо создание нового пространства в другой валюте.
- Автоматический FX, исторические курсы, конвертация отчётов и долги между разными валютами — после MVP. Никаких неподтвержденных курсов валют в приложении.
- CSV/JSON включают код валюты в каждую финансовую запись. В UI суммы отображаются форматтером Intl.NumberFormat с кодом валюты и выбранной локалью.

## 11. Заметка о корректности периодов

- Учет аренды разделяет **полное обязательство** (пользователь видит -750 CZK на старте оплаченной недели) и **расход, относящийся к отчётному периоду** (пропорциональная часть аренды по пересечению дат). Это два представления одной записи, а не два списания.
- Если аренда и отчёт совпадают по периоду, учтена полная стоимость; если не совпадают, ровно соответствующая часть. Для незавершённых месяцев при просмотре «сегодня» не следует выдать полный недельный расход за расход текущего дня.

## 12. Решение принято — 2026-11-06: валюта учёта без FX (FINAL для MVP)

**Выбор пользователя:** валюты CZK/EUR/USD/UAH — для **учёта**, без автоматического пересчёта старых значений. Это заменяет вопросы об альтернативной модели «валюта отображения» в предыдущих версиях.

- При регистрации профиль получает `preferred_currency_code` (по умолчанию `CZK`). Настройка применяется к **будущим** рабочим пространствам; не изменяет валюту существующих денежных операций.
- Каждый workspace фиксирует одну `currency_code`. При создании команда совместно выбирает валюту; уже созданное непустое пространство нельзя перевести в другую валюту одним переключателем. Нужен новый workspace либо специальная процедура миграции в будущем.
- Вся экономика смены, аренды, комиссий и взаиморасчётов внутри workspace рассчитывается в его валюте. При несовпадении валют запись отклоняется, конвертации нет.
- Интерфейс ru/cs/en независим от выбранной валюты. `CZK` не означает чешский язык, `UAH` не означает украинский.
- При экспорте каждой денежной сущности обязательно указывать валюту; при импорте с конфликтом валют отображать явную ошибку.
- Для исторической корректности комиссия сохраняется в снимке смены, суммы — в минимальных единицах; валютный символ не подменяется без изменения исходных денежных данных.

**Критерий готовности:** после изменения `preferred_currency_code` CZK→EUR существующая смена 1 000 CZK продолжает отображаться как 1 000 CZK; новая команда может быть EUR; комбинированной суммы 2 000 в неизвестной валюте не существует.

**Статус:** готово к Phase 1/Foundation. Не включать FX API, автоматическое определение курсов или конвертацию в MVP.
